# KNOWN_ISSUES.md

Format: one entry per issue. State, impact, and whether it blocks a gate.

- CLAUDE.md §7's doc set (README.md, GAME_DESIGN.md, TECHNICAL_ARCHITECTURE.md, RESEARCH.md, MODDING_GUIDE.md, ITEM_CREATION_GUIDE.md, CHARACTER_CREATION_GUIDE.md, ENEMY_CREATION_GUIDE.md, DEVELOPMENT_ROADMAP.md) doesn't exist yet — no prior session (P0.1 through P1.6) created them despite completing the tiers those docs are meant to describe. Not blocking any gate so far since PROGRESS.md's own P3.8 ("All docs complete and accurate") is the dedicated gate for this; flagging so it isn't forgotten and P3.8 doesn't turn into an 8-document cold start.
- Shop item price tags/sale sign (P1.6, src/render/renderer.js) use the same canvas-text approach as the item banner but haven't been visually confirmed via a shop-room screenshot (the smoke test's seeded run didn't land in a shop room). Logic is covered by tests/systems-shop.test.mjs; worth an eyeball check next time a run happens to reach a shop.
- The melee weapon type's ctx (weapons.js's fireMelee, called from player.js's updatePlayer) doesn't carry `player`/`playerHealth`, so killing an `exploder`-behavior enemy with melee fires the explosion event but skips the player-damage part of it (bombs/tears/nova all pass the full ctx and work correctly). Melee isn't granted by any item yet, so this isn't reachable in practice; thread playerHealth into updatePlayer's ctx if/when an item grants the melee weapon type.
- P1.8's boss-room/trapdoor/floor-advance wiring hasn't been visually confirmed in the browser (smoke test's seeded run never reaches a boss room on floor 1, since boss rooms sit at the farthest dead end). Logic is covered by tests/systems-bosses.test.mjs + tests/systems-bossPatterns.test.mjs and the simulate gate's per-boss phase-cycling check; worth a manual playthrough (or a debug `nextfloor`/`tp` console command once P3.3 exists) to eyeball the HP bar, telegraphs, and trapdoor.
- `advanceFloor()` (main.js) is a plain cut to the next floor with no transition visual (no fade, unlike the slide between rooms). Worth revisiting in the P1.10 game-feel pass.
- The death screen (src/ui/screens.js's drawDeathScreen) was verified by code inspection and the smoke test's "zero console errors" check, not an actual eyeballed screenshot — forcing an in-browser player death wasn't practical to script quickly in this session. The menu and pause overlays *were* visually confirmed via a one-off Playwright screenshot. Worth a manual look next time a run actually ends in death during testing.
- (RESOLVED 2026-11-16, P2.8) Floors beyond stage 4 fell back to chapter 1/2 content — fixed by adding chapters 3/4/5 (floor-5..9, 25 enemies, 8 bosses). Floors beyond stage 9 (past the final chapter, which the player shouldn't normally reach since the trapdoor there now ends the run in victory) still fall back to chapter 5's pool/palette rather than anything new; harmless edge case, not expected to be reachable in normal play.
- (RESOLVED, P1.F3) The HUD previously lacked coins/bombs/keys counts, the active item's charge bar, and the consumable slot — all added in the P1.F playtest-fix pass (ui/hudModel.js + ui/hudPanels.js); confirmed still rendering correctly in every P2.6-P2.10 screenshot.
- `tools/simulate.mjs`'s (b) kitchen-sink test (CLAUDE.md §5: "give the player every item at once and simulate 3000 frames of combat") has never actually granted the player any items, in any session back to when it was first written — it only spawns every enemy at once. Found while wiring P2.4's familiars into the gate (which now spawns one familiar per behavior directly, sidestepping this gap rather than fixing it, since a real fix means simulating every active-item effect and weapon-type override too). Not blocking any gate (no crash either way, and real item/weapon-type/synergy coverage exists elsewhere: tests/systems-items.test.mjs, tests/systems-weapons.test.mjs, tests/systems-synergies.test.mjs, and (d)'s full-floor bot genuinely picks up real items from real pools). Worth a real fix: give the player every item via `pickUpItem` before the 3000-frame loop, the same way (d) already does it incrementally via pedestals.
- (P2.6) `tools/simulate.mjs`'s (d) full-floor bot always generates stage-1 floors (`generateFloor(1, floorRng)`), so challenge rooms — gated to stage 2+ — are never exercised by that automated gate, and simulate.mjs's own local `stockRoom` doesn't replicate main.js's "challenge door won't open below full health" gate at all (harmless for the gate's purpose, since the bot's god-mode health never drops anyway, but it means the gate doesn't prove the real gate works end-to-end). Covered instead by tests/systems-specialRooms.test.mjs (wave-spawning logic) and a manual smoke scene (door-tint + the rest of P2.6's art). Worth extending the bot to multi-floor runs if a later session wants automated coverage of floor-2+-only content (challenge rooms, key-locked doors' real floor-2 threshold, etc.).
- (P2.9) A saved run only replays pool-removal for the currently-held trinket/card (plus every seen item id) on restore — a previously-held-then-replaced trinket or already-consumed card that isn't the one currently held can reappear in a future pedestal after a true page-reload Continue, since there's no "all trinkets/cards ever seen" set persisted (only "currently held"). Minor; doesn't break anything structurally, just a small fairness/immersion gap. Worth a dedicated `seenTrinketIds`/`seenCardIds` set in save.js if it ever matters.
- (P2.9) Save/restore is "room entry" granularity, not full fidelity: continuing a saved run always re-stocks the room the player was in (fresh enemy pack), and a revisited-but-previously-stocked room picks a template via a fresh rng stream (so its rock/pit layout may render differently than the original visit, though P1.G1's reachability guarantees mean it can never softlock). Intentional per CLAUDE.md's "mid-run save on room entry" wording, not a bug.
- (P2.9) `src/systems/items.js` (imports familiars.js) and `src/systems/pickups.js`/`enemies.js` have an import-order-sensitive circular dependency: a module importing `Currency` from pickups.js before `ItemInventory` from items.js throws `ReferenceError: Cannot access 'PICKUP_TYPE' before initialization` at load time. Worked around in tests/systems-save.test.mjs by matching the working import order from tests/systems-deals.test.mjs; the underlying cycle itself is untouched. Worth untangling (likely by having enemies.js not import PICKUP_TYPE from pickups.js at module scope, or breaking the items.js -> familiars.js edge) next time it bites a new test file.
- (P1.G1) Boss spawn position is always the room's fixed center (main.js's stockRoom boss branch), with no tile-safety check against that specific tile the way P1.G1 added for normal-room enemy spawns. Not a known bug today (both boss templates keep the center clear — boss-01's `fourCornerRocks` pattern and boss-02's blank layout), but if a future boss template ever puts an obstacle at dead center, the boss would spawn inside it. Worth reusing `findGroundSpawnTile`/`roomReachability` for boss placement if/when P2.8 adds boss templates with center obstacles.
